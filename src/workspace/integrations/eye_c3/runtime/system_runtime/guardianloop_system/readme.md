# GuardianLoop 综合交互候选（2026-10-07）

这是当前已有工程的统一交互规则、本机静音原型和隔离 HDMI 页面回放候选，不是正式上线整机，也不是可载人的轮椅控制系统。本机视频仍是占位区；板端候选可以在同一显示会话中播放已有视频缓存。没有电机、GPIO、音频输出或真实脑电/眼动控制连接。所有脚本页面、点击和模拟标签都不能计入识别准确率。

## 本轮已经实现

入口 `python -m guardianloop_system.preview_server`。只监听电脑 `127.0.0.1`，运行半小时自动退出；终端输出本次访问地址。访问码保存在 URL 片段，请求携带专用头。只提供有限的模拟动作，不接受路径、任意命令或伪造脑电数据。后端可以独立执行 `core.py` 的状态机测试。

沿用既有 `brain_eye_coexist/candidate/eye/src/selection.py` 的三列停留确认、时间戳新鲜度和移开重触发规则；沿用 `wheelchair_ssvep/dry_run_bridge.py` 的 SSVEP 证据门控，不再重新实现一套判据。界面分区与三列判定相同。页面呈现回执之后先给 1.2 秒阅读时间，防止换页后的旧注视立即确认下一项。

- 主页：左方向、中交流表达、右多媒体。
- 方向：8/10/12/14 Hz 分别保留既有前进/后退/左转/右转映射。本原型不闪烁、不发运动命令，需要手动启用虚拟方向。可信证据过期约 300 ms、换页或断流会撤销方向。
- 速度：左加一档、中返回方向、右减一档。仅限 1–3 档虚拟目标，不是 km/h 或电机 PWM。
- 视频：中央观看、不触发选择；左翻页、右评价。
- 翻页：左上一条、中返回、右下一条，选择后返回观看。
- 评价：左好、中返回、右厌倦，记录用户选择并返回观看。
- 表达/歌曲：选择文字或曲目索引，不发声。原型的十条索引不是十个已经上传的真实文件。
- MI 退出：第一段右手确认、可信中性/解除意图间隔、第二段独立右手确认，在 8 秒内完成；窗口必须不重叠、ID 不重复、会话相同且质量/新鲜度合格。换页、断流、异常和超时清除未完成组合。当前没有把左右手二分类的低分或左手预测改名为“正常脑电”。
- 疲劳候选警示阻止方向并保持，确认警示不会自动恢复运动。按用户用途，质量合格的 GAMEEMO boring/horror 条件可作为“无聊／紧张类心情参考”提示选歌，注明模型估计、非本人心情实测，不自动播放；120 秒内不重复提示，不抢占方向/速度页面。本人确认情绪不佳仍可主动进入选歌。

测试：`python -m unittest discover -s guardianloop_system -v`，以及 `node guardianloop_system/test_preview_page.js`。当前 23 项系统 Python 测试与页面脚本检查通过。测试覆盖虚拟菜单、时效/断流、窗口独立性、页面回执、注视不连跳、观看中央重新准备、警示不自动恢复、页面租约与暂停时不转发可选任务包；不是识别性能或实体运动验收。

## 从参考线程确认的边界

已读取用户指定的“情绪，ssvep (2)”线程近期记录。该记录有 Z15→ESP32 五指令的虚拟通信验证，并保留 GPIO 禁用。真实方向辨识、无线失联保护与实际电机接线/制动仍未作为本轮通过项；本轮没有操作 ESP32 或重新读取其固件状态。

现有继电器式轮椅驱动没有验证连续调速能力，不能通过软件界面就宣称加减速已落地，更不能给继电器盲目发送 PWM。必须先确认轮椅控制器的受控调速接口、限速、独立急停及断网停止，再实现真实速度驱动。MI 退出不能作为唯一急停方式。

目前情绪模型的 GAMEEMO 条件标签不是用户本人即时情绪真值。疲劳结果也仅是模型候选，不能展示为医疗结论。右手/正常脑电备选路线需要独立标注的休息样本和误触发率验证；不能仅交换标签或在这轮重新宣称准确率提高。

## 与实际 HDMI 接入的先后顺序

1. 先关闭视频与完整脑电负载竞争的缺口，并把现有显示会话和本状态机组合成唯一的 HDMI 所有者。不同页面不能各自加载 Overlay、各自抢 VDMA；界面字样应缓存，避免逐视频帧重绘文字。方向页面才允许刺激/方向事件，其他页面关闭方向。
2. 在隔离副本接入真实采集状态、原眼控校准及合法 SSVEP/MI 事件。必须有新鲜度、质量、唯一窗口和会话检查。实际 MI 尚没有已验证的中性/解除意图适配器，因此两次右手退出还不能接到实体控制。
3. 先完成“不输出电机”的整机演示和自动故障回放，再另行核对 ESP32 与硬件调速/制动，取得实体测试授权后台架验证。没有这道门槛，不升级为可移动轮椅。

ARM 当前承担脑电滤波、质量检查、情绪/疲劳/SEED/SSVEP/MI 与界面仲裁；现有显示 PL 在隔离播放期间承担 HDMI/VDMA。复用显示 PL 不等于新的滤波/矩阵核已与它整合。本轮没有生成 bitstream、更改模型、烧录 ESP32 或安装开机服务。

视频/缓存证据及仍未通过的帧率在 `docs/PHONE_VIDEO_CHUNK_COEXIST_20261007.md`。目前不能把此原型包装为所有功能都已经完成的正式成品。

## 隔离 HDMI 页面调度

复用 `phone_video_upload/media_player.py` 唯一显示所有者和恢复逻辑；`system_hdmi.py` 缓存中文菜单，切页不另起播放器或重载 PL，视频只写中央 ROI。最新 ROI 为 `(448,245,384,216)`，完全落在中央三分之一列内；既有 640×360 缓存等比例缩放，不跨左右按钮边框。横/竖原始文件的预处理比例、旋转元数据仍需要分别核对，不能因这个 ROI 修复就宣称所有上传格式已通过。

`page_policy.py` 使用板端 monotonic 时钟及 2 秒租约。滤波/质量、主情绪/疲劳与 MI 计算保留；方向页才转发 SSVEP 包并执行候选计算，离开方向页撤销旧频率、暂停该分流，返回必须重新热身。SEED 是非主线诊断，本轮暂停而非伪造有效结果。租约失效时可选任务关闭，原始主采集不丢弃。

显示守护仍执行原有检查，但移到独立线程；检查错误或超过 4 秒未完成的新鲜检查将结束显示会话。中央连续行范围清缓存，不对非连续 ROI 直接执行错误范围的 flush。板端 C 等比例缩放与软件参考、行尾保护和空指针拒绝已通过。

预处理可以用 `repack_cache.py --fit-central` 将已有 640×360 缓存提前缩到 384×216，全部帧核验后再发布清单；播放时不重复缩放，不丢帧或重复插帧以抬高数字，两个缓存块共约 7.6 MiB。画质是中央 384×216，不是完整 720p 视频细节；HDMI 扫描仍为 1280×720。

PL 所有权客户端查询和未修改的正式运行检查一起放入守护线程，仍保留 4 秒新鲜度期限。测得私有状态写盘曾阻塞约 1.23 秒，因此隔离版的实时状态和 2 秒页面租约使用 `/dev/shm/<私有目录名>-player-status.json`、`-system-page.json`；结束撤销租约并保存最终磁盘快照。正式网页和采集服务没有接入这些私有路径。

第一轮 100 秒、十次脚本页面切换只加载一次显示 Overlay，DMA 停止/缓冲释放/正式 PL 恢复均通过。视频平均 13.122 帧/秒、最低完整秒 0 帧，未达到持续 16 帧；原版与调度版共同的 51 个主输出窗口逐项一致。仍未接真实眼动/脑电控制。详细机器证据保存在 `phone_video_upload/output/unified_hdmi_20261007/`，第二轮布局与调度联合测试以该目录最终报告为准。

本轮收尾的内存状态版 `play-system-994c7e21`：显示全部 1210 帧，平均 19.924 fps，最低完整秒 14 帧（启动第 2 秒），其余完整秒 19–21 帧，最大新画面间隔约 0.345 秒。严格“全程至少 16 帧”仍未通过，不写成稳定达标；后续可单独补启动预取。75000 包完整处理，51 个共同主输出窗口仍一致；没有错误/残留子进程，旧结果和页面租约结束撤销。正式 48 文件、启动配置、原视频与服务 PID/重启计数未改变，正式 PL 已恢复。见 `docs/UNIFIED_HDMI_PAGE_SCHEDULE_20261007.md`。
