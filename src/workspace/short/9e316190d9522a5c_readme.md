# GuardianLoop DMA buffer owner — isolated candidate

This is **not deployed**. Do not load `gldma_owner.ko` on the live Z15 merely because it cross-compiles. It assumes a new 64-bit bidirectional simple-DMA + filter Overlay, which has not been programmed or physically validated. The current ARM service and Overlay are untouched.

## Confirmed target and ABI

- Z15 kernel queried read-only: `5.4.0-xilinx-v2020.2`, ARMv7, `CONFIG_DMA_CMA=y`, `CONFIG_MODVERSIONS=y`, `CONFIG_MODULE_FORCE_UNLOAD=y`.
- `gldma_uapi.h` defines ABI 1. Input is exactly 80 signed 64-bit Q16 words, output exactly 80. Each direction has a 640-byte payload inside a 768-byte coherent allocation (64-byte guard on each side). `STATUS` exposes the payload bus address, not the allocation base; the ioctl layout and DMA payload length are unchanged.
- `GLDMA_IOCTL_STATUS` reports `READY`, `RUNNING`, or `UNKNOWN`. `GLDMA_IOCTL_RUN` accepts a complete frame and returns only after both DMA directions report IOC + Idle, no DMA/filter error, expected S2MM length, and valid 40-bit sign extension.
- [`gldma_status.c`](gldma_status.c) is a read-only status utility for a future authorized test; an `O_RDONLY` descriptor is explicitly rejected for `RUN`.
- No `mmap` or direct DMA address control is provided to the worker. Registers are touched only by the module. The former synthetic device and `dma_base`/`gpio_base` module parameters were removed. A custom-compatible, boot-time device-tree node must supply two named MMIO resources and ABI version 1. The isolated [`candidate_static_node.dtsi`](candidate_static_node.dtsi) is **disabled by default** and must not be installed without a matching bit/HWH and boot-order review.
- The isolated BD decodes 64 KiB for each register peripheral, and maps both DMA masters only to the first 1 GiB of HP0 DDR. The driver validates the DT resource bases/sizes against this BD and rejects out-of-range or unaligned allocations, including both guards. `devm_ioremap_resource()` claims both full regions, so a competing kernel driver should fail to bind. This does not prove physical HP0 bus translation or prevent root-level `/dev/mem` access. See [DT_BINDING_RESULT.md](../../output/kernel_owner_offline_20260928/DT_BINDING_RESULT.md) for the earlier binding build and [preboard preparation](../../output/pl_preboard_ready_20260928/RESULTS.md) for the current guarded build.

## Ownership and failure rule

The DT-matched device allocates TX and RX using `dma_alloc_coherent(&pdev->dev, ...)` and holds both for its lifetime. One open file is allowed; a forked/inherited FD cannot submit from another process ID. On first attempted run the module takes an extra reference and **never releases it** in this candidate. A normal `rmmod` should then fail; a worker crash or `SIGKILL` cannot close the kernel-owned buffers. Any frame error, result-delivery failure, or final FD close after the first run locks the module into `UNKNOWN`; all later runs are rejected. The result copy remains under the transaction mutex, so threads sharing the same FD cannot start the next frame before delivery completes. Same open FD can submit multiple verified frames without resetting the stateful filter each time.

This is intentionally conservative. `UNKNOWN` cannot be cleared by DMA reset or PL reset; only a future, separately verified whole-PS/HP recovery design may add such an operation. A normal close after a successful frame also enters `UNKNOWN`, because a new process cannot reconstruct the filter origin/state safely. Removal invalidates surviving descriptors under the transaction mutex and retains coherent pages after any run; a successful probe can never rebind during that module load. This only prevents later driver MMIO or buffer reuse: `remove()` returning `-EBUSY` does not guarantee that the device core retains devres mappings or that in-flight HP0 transactions have drained. Manual `rmmod -f` and runtime removal of the DT node are **not safe**. Use only a non-removable boot-time node after review; never use this as a live DT overlay. The board kernel enables forced module unload, so this is still not a production-grade guarantee against privileged misuse.

## Offline build evidence

`gldma_guard.h` is shared by the module and `test_guard.c`. Guards are initialized only at allocation, checked before submission and after verified completion, and never refreshed between frames. A violation returns `-EOVERFLOW` and latches `UNKNOWN`. The receive payload is poisoned before submission, while DMA is idle, to prevent accepting stale/short receive contents. Guards detect adjacent writes only; they do not establish an IOMMU boundary or prove that HP0 is drained.

`prepare_board_vectors.py` creates synthetic continuous-state golden frames and checks that quantized coefficients match the XPR coefficient file. `gldma_board_check.c` has no default hardware action: `--check-vectors` only validates files. The future `--run-approved` and `--crash-after-approved` modes require separate authorization and a reviewed fresh candidate session. The latter kills a worker only after a verified completed frame, not during an observed in-flight transfer. No physical mode has been executed. The runbook and local recovery files are under `../../output/pl_preboard_ready_20260928/`.

The board's matching kernel build tree was copied **read-only** into `../../output/kernel_owner_offline_20260928/headers`; `modules_prepare` was run only on that local copy. Local WSL cross-compiler is `arm-linux-gnueabihf-gcc`. GCC's hard-float default makes the 5.4 `cc-option` probe pick `armv5t`; `KCFLAGS=-march=armv7-a` is needed for correct ARMv7 assembly. The local host GCC also needs `HOSTCFLAGS=-fcommon` for its old `dtc` parser. These flags affect only the isolated build; no board files were edited.

```bash
gcc -std=c11 -Wall -Wextra -Werror test_policy.c -o /tmp/gldma_policy_host
/tmp/gldma_policy_host
arm-linux-gnueabihf-gcc -std=c11 -Wall -Wextra -Werror -c gldma_status.c -o /tmp/gldma_status_arm.o
make -C /path/to/local/board_headers ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- HOSTCFLAGS=-fcommon modules_prepare
make -C /path/to/local/board_headers M=$PWD ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- HOSTCFLAGS=-fcommon KCFLAGS=-march=armv7-a modules
modinfo -F vermagic gldma_owner.ko
python3 test_binding_contract.py  # WSL, requires dtc and fdtget
```

The host test checks ABI sizes and the actual shared policy transitions: READY→RUNNING→READY on verified completion; RUNNING→UNKNOWN on fault; result-delivery failure→UNKNOWN; any close after a run→UNKNOWN; UNKNOWN cannot begin. It does **not** test Linux process death, physical page retention, AXI transaction draining, cache behavior, or actual DDR.

## Remaining admission gates

1. Independent code review of register sequence and compatibility with the actual bit/HWH; exact board part, clock/reset, address map, and coefficient hash must be recorded.
2. No official fix for stock PS7 VIP's 16/80 DDR readback mismatch exists in this project. Retain strict failure; do not mask the last burst. Obtain vendor guidance or independently validate physical DDR.
3. Controlled board test under **separate explicit authorization**: no EEG service overlap, known recovery/SD backup, matching boot DT + bit/HWH, first verify that the disabled template cannot bind, then explicitly enable the exact node in an offline-reviewed boot image; inspect `STATUS`, verify both physical buffers survive `SIGKILL`, concurrent open rejected, no memory reuse while in flight, full 80-word golden output and boundary sentinels.
4. HP0 read/write outstanding observation or a verified PS/HP recovery procedure is still absent. `UNKNOWN` remains terminal. Never infer bus drain merely from DMA `Halted`, `Idle`, or a PL-only reset.
5. A current live DT snapshot and the candidate BD-generated HWH were obtained during the preboard preparation. The disabled-node fixture compiles, but no matching candidate bitstream, approved enabled boot image, or physical HP0 translation proof exists. A production design must control forced unload and DT-node lifetime, prove DMA address translation/coherent mapping on this Zynq, and independently validate hardware. This candidate is a design/compile artifact, **not a deployable safety case**.
