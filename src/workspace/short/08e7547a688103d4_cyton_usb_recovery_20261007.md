# Cyton USB 身份与软件恢复修复（2026-10-07）

## 已确认故障

Z15 本次启动 ID 为 `8f136697-cbea-4b20-a74f-c899978d7f3a`。内核在启动后
7250.718 秒报告 `usb 1-1-port4: disabled by hub (EMI?), re-enabling...`，随后
FTDI 接收器断开两次，最终由 `ttyUSB0` 改为 `ttyUSB1`。原采集服务仍打开
`/dev/ttyUSB0`，持续出现 FileNotFoundError。此证据确认 USB 断开和端口改名，
不能据此确定是供电、接触、电磁干扰、接收器还是驱动导致；“EMI?”不是根因结论。

## 本次正式变更

- 正式版本：`guardianloop-fixed8-usb-recovery-20261007`。
- 只修改正式运行文件 `guardianloop_acquisition.py` 以及相应 release manifest。
- 新服务覆盖文件：`/etc/systemd/system/guardianloop-cyton.service.d/40-usb-recovery.conf`。
- 通过 root-owned 服务环境 `GL_CYTON_PORT` 固定接收器身份
  `/dev/serial/by-id/usb-FTDI_FT231X_USB_UART_D309LDXY-if00-port0`，不固定 ttyUSB 编号。
- 接收器未出现时低开销等待，状态明确无效，不回退到其他串口。
- 真实串口故障仍使采集退出，由既有 `Restart=always`、`RestartSec=15` 重新启动。
- `KillMode=mixed` 让主进程先关闭其读串口、遥测与 MI 子进程。
- 未合并较早隔离候选的滤波/重置优化；模型、阈值、通道、PL、USB 驱动与省电策略均未修改。

## 验证边界

板端 19 项测试通过：身份选择、显式串口覆盖、缺设备时清除旧预测、虚拟设备改名、
串口 EOF/I/O/队列故障、无线静默与恢复。测试使用临时文件、Linux 管道和虚拟数据，
不操作真实 USB 或 PL。

修复后真实采集主进程 21306 完成 15/15 校准并产生正常预测；计划内退出时共处理
42000 包，坏字节、丢包、序号缺口均为 0。随后仅向采集主进程发送一次 SIGTERM，
正常退出，由 systemd 自动启动进程 24854；重新找到同一 by-id 身份并开始真实采集。
这是软件自动重启验证，不是一次真实 USB 拔插验证，也不证明以后不会再发生 USB 异常。
计划内重启会正常清除校准；并未保留断流前基线冒充连续采集。

序号缺口均为 0，primary_stream_resets 为 0，未记录新的 USB 断开。

## 随后发生的另一类掉灯：队列满，而非新的端口改名

同一启动中，进程 24854 在 9171.939547 秒报告 `queue_full` / `Full`，随后正常退出，
由 systemd 自动启动进程 11364；NRestarts 从 31 变为 32。内核过滤记录中没有新的
FTDI 断开/重连，by-id 仍指向 ttyUSB1。用户确认红灯自动恢复。

当时已有输入积压，同时运行的软件诊断测试可能增加负载；不能仅以事件先后关系认定
唯一耗时来源。程序退出 finally 中会发送 `s` 停止收包，解释了软件失败也可出现红灯熄灭。
身份恢复修复有效，不意味着输入队列或显示共存性能已经解决。
