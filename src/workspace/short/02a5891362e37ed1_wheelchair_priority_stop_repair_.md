# 手机遥控被历史停止记录反复撤销

## 现场证据

2026-10-15，用户点击手机“前进”后，最新手机队列又变成 STOP。
同一 HDMI 会话 `play-e627d129` 的优先停止文件仍保留旧命令
`5eee3536a40143388d4ff0121aa4f699`；显示回执已被后续 `choose`
命令 `80ed2afac6c74a41bc800d1ce73a4af0` 覆盖。
旧 `pending_stop` 只比较回执 ID，因而重新认定旧 STOP 未执行，持续撤销手动方向。
这是已确认的软件门控错误，不证明此前右轮不转的接线问题已经解决。

## 修改边界

只改变 `phone_video_upload/wheelchair_link.py` 的停止确认与停止原因标注。
`PriorityStop` 保留同一显示会话内已确认的 STOP 身份，不受后续普通回执覆盖。
发送程序重启后，只有当前导航命令与已执行回执 ID 匹配、属于同一会话、
且导航入队时间严格晚于 STOP，才从现有 `PlayerCommands` 的 STOP 优先消费顺序
恢复确认；不凭“回执处理时间较晚”推断，未匹配或缺失证据仍保持停止。
新的 STOP 身份仍优先撤销方向，处理完成也不自动恢复旧手动命令。
明确 STOP 不再被误标为手机心跳丢失，未确认的优先停止标为 `priority_stop_pending`。

未改变 GPIO10–13 映射、ESP32 固件、手动 500 ms 租约、手机 750 ms 心跳期限，
未重启 HDMI、眼控或脑电采集，未重载 PL，未向实体接收器发送方向／许可指令。
